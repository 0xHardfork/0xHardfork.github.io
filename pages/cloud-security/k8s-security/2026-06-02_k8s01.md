## 🧠 Concept Overview

Configuration and secret management is where a staggering number of real-world Kubernetes breaches begin. The root cause is almost always the same: developers treat Kubernetes Secrets like they're actually secret, when by default they're just base64-encoded data sitting unencrypted in etcd — readable by anyone with etcd access or broad RBAC permissions. Before we get into what's broken, though, we need to understand the *what* and *why* of ConfigMaps and Secrets from first principles.

### The Core Problem: Configuration Coupling

In the old world of monolithic apps, configuration was typically baked directly into the application binary, read from a config file on the same server, or pulled from environment variables set in deployment scripts. When you containerize that application, you hit a fundamental tension: **container images are immutable** (or should be), but configuration changes constantly across environments (dev, staging, prod). You can't re-build your image every time a database host changes.

Kubernetes solves this through two resource types:
- **ConfigMap**: For non-sensitive configuration data (e.g., feature flags, API endpoints, log levels, app.properties files)
- **Secret**: For sensitive data (e.g., database passwords, API tokens, TLS certificates, SSH keys)

The logical separation matters enormously from a security posture: you can apply strict RBAC permissions to Secrets while leaving ConfigMaps more broadly readable for debugging. In practice, though, this boundary is frequently violated — we'll cover that extensively.

### ConfigMaps — Anatomy and Deep Dive

A ConfigMap is a namespaced Kubernetes object that stores arbitrary key-value pairs. The data can be:
- **Plain strings** (e.g., `LOG_LEVEL=debug`, `API_ENDPOINT=https://api.example.com`)
- **Multi-line strings** (e.g., full nginx.conf files, Java properties files, shell scripts)
- **Binary data** (base64-encoded, stored under `binaryData` key)

Here's the complete anatomy of a ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: production
  labels:
    app: web-service
    env: production
data:
  # Single-value keys — these become environment variables or file contents
  LOG_LEVEL: "info"
  API_ENDPOINT: "https://api.internal.example.com"
  MAX_CONNECTIONS: "100"
  FEATURE_NEW_UI: "true"

  # Multi-line values — these are typically mounted as files
  nginx.conf: |
    server {
      listen 80;
      server_name _;
      location /health {
        return 200 'OK';
      }
      location / {
        proxy_pass http://backend:8080;
      }
    }

  app.properties: |
    spring.datasource.url=jdbc:postgresql://db:5432/myapp
    spring.datasource.username=appuser
    cache.ttl.seconds=300
    logging.level.root=INFO

binaryData:
  # Binary values stored as base64 (e.g., small certificates, non-UTF8 files)
  logo.png: "iVBORw0KGgoAAAANSUhEUgAA..."
```

**The `data` vs `binaryData` distinction**: `data` values must be valid UTF-8 strings. If you need to store binary content (images, compiled configs), use `binaryData` where values are base64-encoded. The kubelet decodes them transparently when mounting as files.

**Immutable ConfigMaps**: Starting from Kubernetes 1.21, you can mark a ConfigMap as `immutable: true`. This:
1. Prevents any updates to the ConfigMap data
2. Causes the kubelet to **stop watching** the ConfigMap for changes (reducing API server load at massive scale)
3. Enforces a deliberate deploy-new-ConfigMap-then-update-Pod workflow

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v2.1.0
immutable: true
data:
  LOG_LEVEL: "warn"
```

### Consuming ConfigMaps — Three Patterns

There are three ways a Pod can consume a ConfigMap, each with different trade-offs:

#### Pattern 1: Environment Variables (per-key injection)

The most common, but also the most dangerous pattern from a security perspective:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
spec:
  containers:
    - name: app
      image: myapp:v1.2.0
      env:
        # Inject specific keys as named env vars
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
        - name: API_URL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: API_ENDPOINT
              optional: true  # Pod starts even if key doesn't exist
```

**Why `optional: true` matters**: Without it, if the ConfigMap or key doesn't exist, the Pod fails to start with `CreateContainerConfigError`. In production, missing ConfigMaps can cause cascading deployment failures.

#### Pattern 2: `envFrom` — Bulk Environment Variable Injection

Inject ALL keys from a ConfigMap as environment variables at once:

```yaml
spec:
  containers:
    - name: app
      image: myapp:v1.2.0
      envFrom:
        - configMapRef:
            name: app-config
          prefix: "APP_"   # optional prefix to avoid name collisions
        - configMapRef:
            name: shared-config
            optional: true
```

⚠️ **Security Warning**: `envFrom` is convenient but dangerous because:
1. If the ConfigMap later adds a key like `PATH` or `LD_PRELOAD`, it silently overwrites critical system variables
2. You can't easily audit what environment variables a container actually has without running `kubectl exec <pod> -- env`
3. If a ConfigMap is accidentally replaced with a Secret (it happens!), all secret values become visible in `kubectl describe pod`

#### Pattern 3: Volume Mounts (recommended for files and dynamic updates)

Mount the ConfigMap as a directory where each key becomes a filename and the value becomes the file content:

```yaml
spec:
  containers:
    - name: nginx
      image: nginx:1.25-alpine
      volumeMounts:
        - name: nginx-config
          mountPath: /etc/nginx/conf.d   # entire ConfigMap mounted here
          readOnly: true
        - name: app-settings
          mountPath: /etc/app/settings.properties
          subPath: app.properties        # mount ONLY this key as a single file
          readOnly: true
  volumes:
    - name: nginx-config
      configMap:
        name: nginx-config-cm
        defaultMode: 0444  # read-only for all users (octal!)
        items:             # optional: only mount specific keys
          - key: nginx.conf
            path: default.conf   # rename the file in the volume
    - name: app-settings
      configMap:
        name: app-config
```

**The magic of volume-mounted ConfigMaps**: When the ConfigMap is updated, Kubernetes automatically propagates the updated file to running Pods — **without a restart** — within the `syncPeriod` (default ~1 minute). This enables hot-config-reload patterns for applications that watch their config files (nginx -s reload, Spring Boot Actuator refresh, etc.).

⚠️ **`subPath` caveat**: When you use `subPath` to mount a single file, **automatic updates do NOT work**. The file is bound at mount time and never updated. This is a subtle, well-known Kubernetes gotcha that has caused serious incidents.

### Kubernetes Secrets — The Critical Security Reality

Let's be brutally honest about what Secrets actually are by default:

**A Kubernetes Secret is base64-encoded data stored as a plaintext JSON blob in etcd.**

Base64 is *encoding*, not *encryption*. `echo "cGFzc3dvcmQ=" | base64 -d` gives you `password`. Anyone with:
- Direct etcd access (e.g., etcd port 2379 is exposed)
- `get/list` RBAC verb on `secrets` resource
- Access to the filesystem where etcd data is stored
- Access to etcd snapshots (backups!)

…can trivially read every Secret in the cluster.

Despite this, Secrets are still better than ConfigMaps for sensitive data because:
1. You can apply stricter RBAC (`secrets` is a separate resource type from `configmaps`)
2. API server audit logs distinguish Secret accesses
3. They can be replaced with encrypted backends (etcd encryption at rest, KMS providers — covered in Day 22-23)
4. `kubectl describe` and many tools redact Secret values (though `kubectl get secret -o yaml` shows them)
5. Kubernetes supports plugging in External Secret Operators (Vault, AWS Secrets Manager — Day 24)

#### Secret Types — The Full Taxonomy

Kubernetes has several built-in Secret types, each with a different validation schema:

| Type | `type` field | Purpose |
|------|------|------|
| Generic / Opaque | `Opaque` (default) | Arbitrary key-value data |
| TLS certificate | `kubernetes.io/tls` | `tls.crt` + `tls.key` |
| Docker registry | `kubernetes.io/dockerconfigjson` | Image pull credentials |
| ServiceAccount token | `kubernetes.io/service-account-token` | Auto-created SA tokens (legacy) |
| Basic HTTP auth | `kubernetes.io/basic-auth` | `username` + `password` |
| SSH private key | `kubernetes.io/ssh-auth` | `ssh-privatekey` |
| Bootstrap token | `bootstrap.kubernetes.io/token` | Node bootstrap credentials |

The `type` field is used by the API server to validate required fields (e.g., `kubernetes.io/tls` Secrets must have both `tls.crt` and `tls.key`). For everything else, use `Opaque`.

#### Creating Secrets — All the Ways

```bash
# 1. From literal values (RECOMMENDED for one-off ops — avoids writing to disk)
kubectl create secret generic db-credentials \
  --from-literal=DB_USER=appuser \
  --from-literal=DB_PASS=s3cur3P@ssw0rd \
  --from-literal=DB_HOST=postgres.internal \
  -n production

# 2. From files (e.g., TLS certificates, SSH keys)
kubectl create secret generic tls-cert \
  --from-file=tls.crt=./certs/server.crt \
  --from-file=tls.key=./certs/server.key \
  -n production

# 3. TLS Secret shorthand
kubectl create secret tls my-tls-secret \
  --cert=./certs/server.crt \
  --key=./certs/server.key

# 4. Docker registry credentials
kubectl create secret docker-registry registry-creds \
  --docker-server=registry.example.com \
  --docker-username=robot$ci-user \
  --docker-password=my-registry-token \
  --docker-email=ci@example.com

# NEVER DO THIS — plain YAML with unencoded secrets committed to Git:
# kubectl apply -f secret.yaml  (where the file has base64 values in your repo)
```

#### Anatomy of a Secret YAML (and why you rarely write them manually)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: production
  annotations:
    # Track rotation metadata
    last-rotated: "2026-06-01"
    rotation-by: "ops-team"
type: Opaque
data:
  # Values MUST be base64-encoded in YAML manifests
  # echo -n "appuser" | base64  →  YXBwdXNlcg==
  DB_USER: YXBwdXNlcg==
  DB_PASS: czNjdXJlUEBzc3cwcmQ=
  DB_HOST: cG9zdGdyZXMuaW50ZXJuYWw=
stringData:
  # stringData is WRITE-ONLY — you can provide plaintext here
  # Kubernetes base64-encodes it before storing; it appears in `data` on read
  DB_PORT: "5432"
  CONNECTION_STRING: "postgresql://appuser:s3cur3P@ssw0rd@postgres.internal:5432/myapp"
```

**`stringData` is your friend**: When writing Secret manifests, use `stringData` instead of `data` to avoid manually base64-encoding. But remember: these are **still stored as base64 in etcd** and visible as base64 when you `kubectl get secret -o yaml`. Never commit YAML files with `stringData` containing real credentials to Git.

### Consuming Secrets — Same Patterns, Higher Stakes

The consumption patterns are identical to ConfigMaps but with critical security differences:

#### Environment Variables (convenient but risky)

```yaml
spec:
  containers:
    - name: app
      image: myapp:v1.2.0
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: DB_PASS
      envFrom:
        - secretRef:
            name: db-credentials   # DANGEROUS: bulk-injects all secret keys
```

**Why environment variables for Secrets are risky**:
1. **Process visibility**: `cat /proc/<PID>/environ` from within the same PID namespace exposes all env vars. Inside a container, that PID namespace includes your app's process.
2. **Child process inheritance**: Environment variables are inherited by all child processes. If your app forks a shell (common in legacy apps), the secrets leak to that shell.
3. **Crash dump exposure**: Many crash reporting tools (Sentry, Datadog APM) capture environment variables in error reports — sending your secrets to a third party.
4. **kubectl describe exposure**: `kubectl describe pod <name>` shows env var *names* but NOT values — however, operators might accidentally log them.
5. **`kubectl set env` accidental exposure**: Operations like `kubectl set env deployment/app --list` print all env vars, including those sourced from Secrets.

#### Volume Mounts (preferred for secrets)

```yaml
spec:
  containers:
    - name: app
      image: myapp:v1.2.0
      volumeMounts:
        - name: db-creds
          mountPath: /run/secrets/db    # /run/secrets is tmpfs on Linux — not persisted to disk
          readOnly: true                # ALWAYS readOnly for secrets
  volumes:
    - name: db-creds
      secret:
        secretName: db-credentials
        defaultMode: 0400              # owner read-only (most restrictive)
        items:
          - key: DB_PASS
            path: password             # mounted as /run/secrets/db/password
          - key: DB_USER
            path: username
```

**Why `/run/secrets` and tmpfs?** In Linux, `/run` is typically a `tmpfs` mount — an in-memory filesystem that doesn't persist to disk. Kubernetes mounts Secret volumes as `tmpfs` automatically (you can verify with `mount | grep secrets` inside a container). This means the secret never touches the node's physical disk.

**Projected Volume — combining multiple sources**:

```yaml
volumes:
  - name: combined-secrets
    projected:
      sources:
        - secret:
            name: db-credentials
        - secret:
            name: api-tokens
        - configMap:
            name: app-config
        - serviceAccountToken:       # Projected SA token (time-limited, audience-bound)
            audience: "api.example.com"
            expirationSeconds: 3600
            path: token
```

Projected volumes let you combine Secrets, ConfigMaps, and ServiceAccount tokens into a single mount point — crucial for workload identity patterns.

### Image Pull Secrets — A Frequently Forgotten Attack Surface

When your cluster needs to pull images from a private registry, it uses `imagePullSecrets`:

```yaml
# First, create the registry credential Secret
kubectl create secret docker-registry my-registry-creds \
  --docker-server=registry.example.com \
  --docker-username=robot$deploy \
  --docker-password=<registry-token>

# Reference it in your Pod spec
spec:
  imagePullSecrets:
    - name: my-registry-creds
  containers:
    - name: app
      image: registry.example.com/myteam/app:v1.2.0
```

**Better practice**: Attach `imagePullSecrets` to the namespace's `default` ServiceAccount so every Pod in that namespace can pull automatically:

```bash
kubectl patch serviceaccount default \
  -n production \
  -p '{"imagePullSecrets": [{"name": "my-registry-creds"}]}'
```

**Attack angle**: An attacker who can `get` the `docker-registry` Secret can extract the raw `.dockerconfigjson` and use it to authenticate to your registry — potentially pulling proprietary images or pushing malicious ones.

```bash
# Extract and decode registry credentials from a Secret
kubectl get secret my-registry-creds \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .
```

### The Security Hierarchy — Getting Progressively Better

Here's the realistic spectrum of secret management in Kubernetes, from terrible to excellent:

| Level | Approach | Risk |
|---|---|---|
| ❌ Worst | Secrets in container image ENV, in Dockerfile | Anyone with image access reads creds; `docker history` reveals them |
| ❌ Bad | Secrets as ConfigMaps | No access differentiation; `kubectl get cm` shows plaintext |
| ⚠️ Default | Kubernetes Secrets (base64 in etcd) | Base64 ≠ encryption; accessible to anyone with etcd access or broad RBAC |
| ✅ Better | Secrets + etcd encryption at rest | Encrypted in storage; still exposed in memory at decryption time |
| ✅ Best | External secret operators (Vault, AWS SM) | Credentials never stored in etcd; short-lived leases; full audit trail |

---

## 🔑 Key Points

- ConfigMaps store non-sensitive configuration; Secrets store credentials — but Secrets are only base64-encoded by default, **not encrypted**. Etcd access means full exposure.
- Prefer **volume mounts over environment variables** for Secrets: files on `tmpfs` don't appear in process listings, crash dumps, or child process environments.
- `stringData` in Secret YAML lets you write plaintext without manual base64 — but **never commit YAML files with real credentials to Git**.
- `subPath` volume mounts do NOT auto-update when the ConfigMap/Secret changes — use full directory mounts for hot-reload scenarios.
- The `immutable: true` field on ConfigMaps/Secrets prevents accidental modification and reduces kubelet API server pressure at scale.
- Image pull Secrets (`.dockerconfigjson`) are a frequently overlooked attack surface — guard them with strict RBAC and prefer short-lived registry tokens.

### Example 1 — Full ConfigMap-Driven Nginx Configuration (Hot-Reload Pattern)

```yaml
# 1. ConfigMap with nginx config
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
  namespace: production
data:
  nginx.conf: |
    events {
      worker_connections 1024;
    }
    http {
      upstream backend {
        server app-service:8080;
        keepalive 32;
      }
      server {
        listen 80;
        server_name _;
        access_log /dev/stdout combined;
        error_log /dev/stderr warn;

        location /health {
          access_log off;
          return 200 'healthy\n';
          add_header Content-Type text/plain;
        }

        location / {
          proxy_pass http://backend;
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_connect_timeout 5s;
          proxy_read_timeout 30s;
        }
      }
    }

  upstream.conf: |
    # Additional upstream config that can be hot-reloaded
    proxy_cache_path /tmp/nginx_cache levels=1:2 keys_zone=api_cache:10m max_size=100m;

---
# 2. Deployment consuming the ConfigMap
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-proxy
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx-proxy
  template:
    metadata:
      labels:
        app: nginx-proxy
    spec:
      containers:
        - name: nginx
          image: nginx:1.25-alpine
          ports:
            - containerPort: 80
          volumeMounts:
            - name: nginx-config-vol
              mountPath: /etc/nginx          # FULL directory mount — auto-updates!
              readOnly: true
          # Sidecar to watch for config changes and signal nginx
        - name: config-reloader
          image: alpine:3.19
          command:
            - sh
            - -c
            - |
              while true; do
                inotifywait -e modify /etc/nginx/nginx.conf
                echo "Config changed, sending reload signal to nginx..."
                kill -HUP 1  # Signal nginx master to reload workers
              done
          volumeMounts:
            - name: nginx-config-vol
              mountPath: /etc/nginx
              readOnly: true
      volumes:
        - name: nginx-config-vol
          configMap:
            name: nginx-config
            defaultMode: 0444
```

**What this demonstrates**: Full directory ConfigMap mount enables automatic config propagation. A config-reloader sidecar uses `inotifywait` to detect the file change and signal nginx to reload without downtime — a production-grade hot-reload pattern used widely in service meshes and proxy deployments.

### Example 2 — Secrets as Volume Mounts with Strict Permissions

```yaml
# 1. Create the database credential Secret (imperative — avoid committing to Git)
# kubectl create secret generic db-creds \
#   --from-literal=username=appuser \
#   --from-literal=password=Sup3rS3cr3tPwd! \
#   --from-literal=host=postgres.prod.svc.cluster.local \
#   --from-literal=port=5432 \
#   -n production

# 2. Create a TLS Secret for mutual TLS with the database
# kubectl create secret tls db-tls \
#   --cert=./certs/client.crt \
#   --key=./certs/client.key \
#   -n production

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-server
  template:
    metadata:
      labels:
        app: api-server
    spec:
      serviceAccountName: api-server-sa  # Use a dedicated SA, not default
      automountServiceAccountToken: false # Disable unless needed

      containers:
        - name: api
          image: mycompany/api:v2.3.1
          ports:
            - containerPort: 8080

          # ConfigMap for non-sensitive config via envFrom (OK here — no secrets)
          envFrom:
            - configMapRef:
                name: api-config
                # prefix: "APP_"  # uncomment to namespace env vars

          # Secrets as individual env vars for compatibility with legacy apps
          # ONLY if volume mounts are not an option
          env:
            - name: DB_HOST
              valueFrom:
                secretKeyRef:
                  name: db-creds
                  key: host

          # Secret files mounted to tmpfs
          volumeMounts:
            - name: db-credentials
              mountPath: /run/secrets/db   # tmpfs — not persisted to disk
              readOnly: true               # ALWAYS readOnly
            - name: db-tls
              mountPath: /run/secrets/tls
              readOnly: true

          # Application reads credentials from files:
          # /run/secrets/db/username
          # /run/secrets/db/password
          # /run/secrets/tls/tls.crt
          # /run/secrets/tls/tls.key

          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

          securityContext:
            runAsNonRoot: true
            runAsUser: 1000
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false

      volumes:
        - name: db-credentials
          secret:
            secretName: db-creds
            defaultMode: 0400         # -r-------- (owner read-only)
            items:
              - key: username
                path: username
              - key: password
                path: password
              # Do NOT mount 'host' and 'port' here if injected via env

        - name: db-tls
          secret:
            secretName: db-tls
            defaultMode: 0400
```

**What this demonstrates**: Defense-in-depth for secret consumption — file-based secrets on tmpfs with `0400` permissions, `readOnlyRootFilesystem` to prevent writes, non-root user, and no auto-mounted SA token. The application reads secrets from files (a pattern Go, Java, Node, and Python all support natively) rather than environment variables.

### Example 3 — Detecting Secret Misuse: Extracting and Auditing Secrets

```bash
# ── As a cluster admin / red team: Reading all secrets in a namespace ──

# List all secrets (names, types, ages)
kubectl get secrets -n production

# Read a specific secret in base64 (then decode it)
kubectl get secret db-creds -n production -o jsonpath='{.data.password}' | base64 -d
echo  # add newline

# Dump ALL data from a secret at once
kubectl get secret db-creds -n production -o json | \
  jq '.data | map_values(@base64d)'

# List ALL secrets across ALL namespaces (requires ClusterRole)
kubectl get secrets --all-namespaces -o json | \
  jq '.items[] | {ns: .metadata.namespace, name: .metadata.name, type: .type}'

# ── Find secrets exposed as environment variables in running pods ──
# This is a powerful audit technique — check all pods for secretKeyRef usage
kubectl get pods --all-namespaces -o json | \
  jq '.items[] | select(.spec.containers[].env[]?.valueFrom.secretKeyRef != null) |
    {pod: .metadata.name, ns: .metadata.namespace}'

# ── Check if a pod can read secrets (RBAC audit) ──
kubectl auth can-i get secrets -n production --as=system:serviceaccount:production:api-server-sa

# ── Find ConfigMaps that look like they contain secrets ──
# (keywords: password, token, key, secret, credential)
kubectl get configmaps --all-namespaces -o json | \
  jq '.items[] | select(
    (.data // {}) | to_entries[] |
    .key | test("(?i)(password|token|secret|key|credential)")
  ) | {ns: .metadata.namespace, name: .metadata.name}'

# ── Verify a Secret is mounted as tmpfs inside a pod ──
kubectl exec -n production deploy/api-server -- \
  mount | grep "/run/secrets"
# Expected output: tmpfs on /run/secrets/db type tmpfs (ro,relatime)

# ── Check file permissions on mounted secrets ──
kubectl exec -n production deploy/api-server -- \
  ls -la /run/secrets/db/
# Expected: -r-------- 1 1000 1000 ... password
#           -r-------- 1 1000 1000 ... username
```

**What this demonstrates**: Both the attacker's view (how easy it is to read secrets with basic permissions) and the defender's view (how to audit secret exposure in a running cluster). These commands are your first stop during a K8s security assessment.

### Example 4 — Immutable ConfigMap Rolling Update Pattern

```yaml
# Pattern: Name ConfigMaps with version suffix, deploy new version, update Deployment

# v1 ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v1   # versioned name
immutable: true          # cannot be changed
data:
  LOG_LEVEL: "info"
  CACHE_TTL: "300"

---
# v2 ConfigMap (new version — create alongside, don't replace)
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v2
immutable: true
data:
  LOG_LEVEL: "warn"      # changed
  CACHE_TTL: "600"       # changed
  NEW_FEATURE: "enabled" # added

---
# Deployment references the versioned ConfigMap
# Rolling update: just change app-config-v1 → app-config-v2 in the volume ref
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      volumes:
        - name: config
          configMap:
            name: app-config-v2   # ← update this to roll config
```

```bash
# Rolling update workflow
kubectl apply -f configmap-v2.yaml           # Create new immutable ConfigMap
kubectl set volume deployment/my-app \
  --overwrite \
  --add \
  -t configmap \
  --configmap-name=app-config-v2 \
  --name=config \
  --mount-path=/etc/config

# This triggers a rolling update of all pods to pick up the new config
# If something goes wrong:
kubectl rollout undo deployment/my-app       # reverts to previous pod template
# Previous ConfigMap (v1) is untouched (immutable) — easy rollback!
```

**What this demonstrates**: The immutable ConfigMap versioning pattern ensures atomic config changes with safe rollback. It's particularly valuable in GitOps workflows where config changes trigger deployments.

## ⚠️ Common Misconfigurations & Risks

| Misconfiguration | Risk Assessment | Secure Approach |
|---|---|---|
| **Storing real credentials in ConfigMaps** | ConfigMaps have no RBAC distinction from other config; any developer with `get configmaps` can read database passwords | Use `Secret` type; apply RBAC to restrict `get/list` on `secrets` to only the workloads and operators that need it |
| **Using `envFrom` with Secrets** | Bulk-injects all secret keys — if a secret key is added later (e.g., by a platform team), it gets automatically injected into all pods without a manifest change; crash dumps capture all env vars | Inject specific keys with `secretKeyRef` or prefer volume mounts entirely |
| **`defaultMode: 0644` on Secret volumes** | World-readable files — any process running as ANY user in the container can read the secrets | Use `defaultMode: 0400` (owner read-only, matched to `runAsUser` in `securityContext`) |
| **Committing Secret YAML with `stringData` to Git** | Base64 values or plaintext values in version control; git history never forgets — even after deletion | Use sealed-secrets, SOPS, git-crypt, or External Secrets Operator. Never commit plaintext secrets. |
| **Auto-mounted ServiceAccount tokens with broad RBAC** | The default SA token in every pod can be used to call the K8s API — if the SA has overly broad RBAC, a compromised pod becomes a full cluster escalation path | Set `automountServiceAccountToken: false`; create dedicated SAs with minimal permissions |
| **`subPath` mounts with hot-reload expectation** | `subPath` volumes are NOT updated when the ConfigMap changes — silently stale config causes production incidents | Use full directory mounts for auto-update; use restart or re-deploy cycle for `subPath` use cases |
| **No rotation strategy for Secrets** | Static credentials accumulate exposure over time; a leaked credential stays valid indefinitely | Implement rotation with External Secrets Operator + Vault/cloud KMS; set expiry annotations for auditing |

### Exercise 8 — Simulate Secret Rotation with Zero Downtime (Challenge Simulation!)

```bash
# ── ConfigMap operations ────────────────────────────────────────────────────
kubectl create configmap my-cm \
  --from-literal=KEY=VALUE \

  --from-literal=password=S3cr3t \
  --from-file=tls.crt=./cert.pem

  --docker-server=... --docker-username=... --docker-password=...

# Read secret value (decoded)
kubectl get secret my-secret -o jsonpath='{.data.password}' | base64 -d

# Dump all decoded secret data
kubectl get secret my-secret -o json | jq '.data | map_values(@base64d)'

# ── Auditing secrets ──────────────────────────────────────────────────────
# Find pods using secrets as env vars
kubectl get pods -o json | jq '
  .items[] |
  select(.spec.containers[].env[]?.valueFrom.secretKeyRef != null) |
  .metadata.name'

# Check if a service account can read secrets
kubectl auth can-i get secrets -n production \
  --as=system:serviceaccount:production:my-sa

# Verify secret is mounted as tmpfs
kubectl exec <pod> -- mount | grep "/run/secrets"

# Check file permissions on mounted secret
kubectl exec <pod> -- ls -la /run/secrets/

# ── Immutable ConfigMaps ──────────────────────────────────────────────────
kubectl patch configmap my-cm --type merge -p '{"immutable": true}'
```
