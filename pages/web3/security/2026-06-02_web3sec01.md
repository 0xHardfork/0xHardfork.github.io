## 🧠 Concept Overview

Every security property of Ethereum — wallet ownership, transaction integrity, smart contract addresses, digital signatures — rests entirely on two mathematical foundations: **cryptographic hash functions** (specifically Keccak-256) and **Elliptic Curve Digital Signature Algorithm** (ECDSA over the secp256k1 curve). If you don't have these locked down cold, you'll misunderstand every access control vulnerability, every signature replay attack, and every `ecrecover` pitfall that comes later. So let's build this from the ground up.

---

### Part 1: Cryptographic Hash Functions

A hash function takes an arbitrary-length input and produces a fixed-length output (the "digest" or "hash"). A **cryptographic** hash function must satisfy three critical properties that make it useful for security:

#### Property 1: Pre-image Resistance (One-way)
Given a hash output `H`, it must be computationally infeasible to find any input `m` such that `hash(m) = H`. This is what makes password hashing useful — even if an attacker sees your stored hash, they can't reverse it to get your password.

Mathematical intuition: Hash functions work like mixing colors. Given a specific shade of mud, you can't un-mix it back into the original paints.

#### Property 2: Second Pre-image Resistance
Given an input `m1`, it must be infeasible to find a *different* input `m2` (where `m2 ≠ m1`) such that `hash(m1) = hash(m2)`. This prevents an attacker from substituting one signed document for another.

#### Property 3: Collision Resistance
It must be infeasible to find *any two* inputs `m1` and `m2` (both arbitrary) such that `hash(m1) = hash(m2)`. Note: collisions *must* theoretically exist (infinitely many inputs → finite output space), but finding them must be practically impossible. The famous MD5 and SHA-1 algorithms are now broken by collision attacks — they should never be used in security contexts.

---

### Keccak-256: Ethereum's Hash Function

Ethereum uses **Keccak-256** (often mistakenly called SHA3-256 — they're related but subtly different). The Ethereum team chose Keccak-256 *before* NIST standardized SHA-3, and NIST made a slight modification to SHA-3 before finalizing. **Keccak-256 ≠ SHA3-256**. The differences are small but matter for interoperability.

Keccak-256 produces a **256-bit (32-byte) output**. In hex, that's 64 characters. Example:
```
keccak256("") = c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
keccak256("Hello") = 06b3dfaec148fb1bb2b066f10ec285e7c9bf402ab32aa78a5d38e34566810cd2
```

Notice `keccak256("")` is not all zeros — the hash of an empty string is a well-defined constant. This is important in Ethereum: the hash of the empty bytecode is checked when determining if an address is a contract vs EOA.

#### Where Keccak-256 Appears in Ethereum

1. **Transaction Hashing**: Every transaction is identified by `keccak256(rlp(transaction))` — the transaction hash (txHash) you see on Etherscan.
2. **Block Hashing**: Block headers are hashed with Keccak-256 to produce block hashes. Proof-of-Work mining was about finding a nonce that made `keccak256(blockHeader) < target`.
3. **Contract Addresses**: The address of a deployed contract is `keccak256(rlp([deployer_address, nonce]))[12:]` — the last 20 bytes of the Keccak hash of the RLP-encoded deployer address and nonce. This is why `CREATE` addresses are predictable if you know the deployer and nonce.
4. **CREATE2 Addresses**: `keccak256(0xff ++ deployer ++ salt ++ keccak256(bytecode))[12:]` — fully deterministic based on bytecode. This is used extensively in factory patterns and by Uniswap V2/V3.
5. **Storage Slot Computation**: In mappings, the storage slot for key `k` is `keccak256(abi.encode(k, slot))`. This is critical for EVM storage layout attacks.
6. **`msg.sig` Function Selectors**: Function selectors are the first 4 bytes of `keccak256("functionName(paramType1,paramType2)")`. That's how the EVM dispatches calls to the right function.
7. **Event Topics**: `keccak256("EventName(type1,type2)")` is `topics[0]` in emitted event logs.
8. **EIP-712 Structured Data Hashing**: Type hashes, domain separators — all built on Keccak-256.

### The EVM `keccak256` Opcode

At the opcode level, `KECCAK256` (opcode `0x20`, formerly called `SHA3`) takes two stack arguments: a memory offset and a byte length. It hashes that region of memory and pushes the 32-byte result. This costs **30 gas + 6 gas per 32-byte word** of input data — not cheap, which is why you see gas optimization tricks around hashing.

In Solidity, you use it via the built-in:
```solidity
bytes32 h = keccak256(abi.encodePacked(data));
// or
bytes32 h = keccak256(abi.encode(data));
```

**`abi.encodePacked` vs `abi.encode` — a critical security difference**:
- `abi.encode`: Pads all types to 32 bytes. Unambiguous. No hash collisions between different argument structures.
- `abi.encodePacked`: Concatenates the raw bytes tightly. Efficient, but **can cause hash collisions** with dynamic types. `abi.encodePacked("ab", "c") == abi.encodePacked("a", "bc")` — both produce `0x616263`. This is the root cause of a real vulnerability class we'll cover in Phase 16.

### Part 2: Elliptic Curve Cryptography (ECC)

#### Why Elliptic Curves?

Classical RSA public-key cryptography requires very large key sizes (2048+ bits) for security. Elliptic Curve Cryptography achieves equivalent security with much smaller keys (256 bits). This is why Ethereum uses ECC — transaction signatures are compact, which is crucial for on-chain data costs.

An elliptic curve over a field is defined by the equation:
```
y² = x³ + ax + b  (mod p)
```

For Ethereum's **secp256k1** curve specifically:
- `a = 0`, `b = 7`
- Equation: `y² = x³ + 7 (mod p)`
- `p` = a specific 256-bit prime: `0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEFFFFFC2F`
- Generator point `G`: a specific point on the curve that serves as the "base" for all key generation
- Order `n`: the number of points in the group (`0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141`)

The key insight: the curve isn't a smooth parabola over real numbers — it's a set of discrete points satisfying the equation over a finite field modulo a prime. This creates a group structure with defined point addition.

#### Elliptic Curve Point Addition

Two points on the curve, `P` and `Q`, can be "added" to produce a third point `R = P + Q`. The geometric rule:
- Draw a line through P and Q
- Find the third intersection with the curve
- Reflect that point across the x-axis → that's R

Special cases:
- If `P = Q` (doubling): draw the tangent at P instead
- If `P = -Q` (inverse points): the sum is the "point at infinity" O (the identity element)

Scalar multiplication `k * G` means adding G to itself k times. This is the **one-way trapdoor** of ECC: given `k` and `G`, computing `k * G` is fast (via double-and-add algorithm — O(log k) operations). But given `G` and `k * G`, finding `k` is the **Elliptic Curve Discrete Logarithm Problem (ECDLP)** — computationally infeasible for secp256k1's key size. The best known algorithm takes approximately 2^128 operations. That's the trapdoor that makes ECC secure.

### Part 3: Ethereum Key Pairs & Addresses

#### Key Generation

1. **Private Key**: A randomly chosen 256-bit integer `k`, where `1 ≤ k < n` (n is the curve order). This is just a big random number. In practice, your wallet uses a CSPRNG (cryptographically secure random number generator) to pick it. Security note: if `k = 0` or `k ≥ n`, it's invalid. If your entropy source is weak, your private key is predictable — this has caused real wallet thefts.

2. **Public Key**: Computed as `K = k * G` — scalar multiplication of the generator point. K is an (x, y) pair of coordinates, each 256 bits. Uncompressed: `04 || x || y` (65 bytes). Compressed (using the fact that y can be derived from x): `02 || x` or `03 || x` (33 bytes, depending on the parity of y).

3. **Ethereum Address**: `addr = keccak256(K)[12:]` — take the Keccak-256 hash of the 64-byte uncompressed public key (WITHOUT the `04` prefix), then take the **last 20 bytes** (160 bits). This discards the first 12 bytes of the hash. The `0x` prefix you see is just display convention. EIP-55 adds a checksum via mixed-case encoding.

```
private key k = 0xf8f8a2f43c8376ccb0871305060d7b27b0554d2cc72bccf41b2705608452f315
public key K  = (x, y) = (6e145ccef1033dea239875dd00dfb4fee6e3348b84985c92f103444683bae07b,
                           1701a702e81a20b3c92a6e4e6ca9f9a1219a26cb52498e3f3a7f96d18e6f89cf)
address       = keccak256(x||y)[12:] = 0x001d3F1ef827552Ae1114027BD3ECF1f086bA0F9
```

### Part 4: ECDSA — The Digital Signature Algorithm

ECDSA allows you to prove you control a private key without revealing it. This is used for every Ethereum transaction and most access control in smart contracts.

#### Signing (done by the signer's wallet/software)

1. **Hash the message**: `z = keccak256(message)`. In Ethereum, raw transaction data is hashed. For personal messages, the EIP-191 prefix `"\x19Ethereum Signed Message:\n" + len(message)` is prepended first (to prevent signing transactions by accident).

2. **Generate a random nonce `r_nonce`**: A cryptographically random 256-bit integer. **Critical**: this nonce must NEVER be reused. If the same nonce is used to sign two different messages with the same private key, the private key can be extracted mathematically. This is not theoretical — the PlayStation 3 private key was extracted this way, and several Ethereum wallets have been drained through nonce reuse in buggy signing implementations.

3. **Compute `R = r_nonce * G`**: Scalar multiply the random nonce with the generator.

4. **Signature components**:
   - `r = R.x mod n` (the x-coordinate of R, modulo curve order)
   - `s = r_nonce⁻¹ * (z + r * k) mod n` (the signature scalar)
   - `v = 27 or 28` (recovery ID — indicates which of the two possible public keys matches)

The full signature is `(v, r, s)`, 65 bytes total. In Ethereum, this is appended to transaction data.

#### Verification (done by the EVM and `ecrecover`)

Given message hash `z`, signature `(v, r, s)`, and claimed public key `K`:
1. Compute `u1 = s⁻¹ * z mod n` and `u2 = s⁻¹ * r mod n`
2. Compute `R' = u1 * G + u2 * K`
3. Verify `R'.x mod n == r`

If it matches, the signature is valid. The EVM does this for every transaction — it recovers the signing address from the signature and checks it has sufficient balance and correct nonce.

#### `ecrecover` in Solidity — Your Key Security Tool (and Attack Surface)

`ecrecover(bytes32 hash, uint8 v, bytes32 r, bytes32 s)` is a **Solidity precompile** (at address `0x1`) that recovers the signing address from a hash and signature components:

```solidity
// Returns the Ethereum address that signed the message
address signer = ecrecover(messageHash, v, r, s);
```

**Critical security properties and pitfalls**:

1. **Returns `address(0)` on failure, not a revert**: If the signature is malformed or invalid, `ecrecover` returns `address(0)` — the zero address. If your code doesn't check for this, an attacker can submit garbage signatures and potentially pass authentication if address(0) has special permissions (some contracts whitelist it accidentally).

2. **ECDSA Malleability**: For any valid signature `(v, r, s)`, the signature `(v', r, n - s)` is ALSO a valid signature for the same message (where `v'` flips the v bit). This means one signed message has TWO valid signatures! If your contract uses the full signature bytes as a nonce to prevent replay, an attacker can submit the second valid form of the same signature as a "fresh" signature. OpenSea's NFT marketplace was affected by this — NFT listings could be resold using the malleated signature even after the owner thought they'd cancelled. Fix: use OpenZeppelin's ECDSA library which enforces `s` is in the lower half of the curve (`s <= n/2`).

3. **Missing nonce / chainID in signed data**: If your signed message doesn't include a nonce and/or chain ID, the same signature can be replayed: across transactions, across chains (mainnet/testnet), or after the contract is redeployed. EIP-712 and EIP-2612 were specifically designed to solve this.

4. **Front-running ecrecover-based authentication**: On-chain signature verification is public — a watching attacker can copy your valid signature from the mempool and submit it themselves in the same block (with higher gas). This breaks "first come, first served" NFT minting and similar patterns.

### Part 5: EIP-191 & EIP-712 — Structured Signing Standards

Raw `ecrecover` on raw data is dangerous. These EIPs standardize how messages are hashed for signing.

#### EIP-191: Personal Message Signing

Prevents a user from accidentally signing an Ethereum transaction (which starts with an RLP header) via their wallet's "Sign Message" function. Prepends a magic string:

```
"\x19Ethereum Signed Message:\n" + len(message_bytes) + message_bytes
```

In Solidity:
```solidity
bytes32 ethSignedHash = keccak256(abi.encodePacked(
    "\x19Ethereum Signed Message:\n32",
    originalMessageHash
));
address signer = ecrecover(ethSignedHash, v, r, s);
```

MetaMask's `eth_sign` and `personal_sign` both use this format. When you call `web3.eth.sign(account, message)`, the wallet applies the EIP-191 prefix automatically.

#### EIP-712: Typed Structured Data Hashing

EIP-712 is the gold standard for on-chain signature verification. It prevents cross-contract replay attacks by including a **domain separator** in every signed hash. Key components:

1. **Domain Separator**: `keccak256(abi.encode(domainTypeHash, nameHash, versionHash, chainId, address(this)))` — binds the signature to a specific contract, chain, and version.

2. **Type Hash**: `keccak256("Transfer(address to,uint256 amount,uint256 nonce)")` — encodes the structure of the data being signed.

3. **Struct Hash**: `keccak256(abi.encode(typeHash, to, amount, nonce))` — hashes the actual data.

4. **Final Hash**: `keccak256("\x19\x01" || domainSeparator || structHash)` — the thing that's actually signed and passed to `ecrecover`.

EIP-712 is used by ERC20's `permit` function (EIP-2612), Uniswap's Permit2, Seaport (OpenSea's marketplace), and most modern DeFi protocols.

### Part 6: How Ethereum Transactions Are Signed

Tying it all together — here's what happens when you hit "Send" in MetaMask:

1. **Transaction fields assembled**: `{nonce, gasPrice, gasLimit, to, value, data, chainId, 0, 0}` (EIP-155 adds chainId to prevent replay across chains — before EIP-155, the same signed transaction was valid on ETH and ETC).

2. **RLP encoding**: The fields are encoded using Recursive Length Prefix (RLP) — Ethereum's binary serialization format.

3. **Keccak256 hash**: `txHash = keccak256(rlp(transaction))` — this is what you actually sign, NOT the raw transaction bytes.

4. **ECDSA signing**: Your private key signs `txHash`, producing `(v, r, s)`.

5. **Broadcast**: The signed transaction `{nonce, gasPrice, gasLimit, to, value, data, v, r, s}` is broadcast to the network. Nodes verify the signature and recover your address to check balance and nonce.

## 🔑 Key Points

- **Keccak-256 ≠ SHA3-256**: They're siblings, not twins. Ethereum uses Keccak-256 (pre-NIST standardization). Using the wrong one in off-chain code produces mismatched hashes that break verification.
- **`address` = last 20 bytes of `keccak256(pubkey)`**: Knowing someone's address does NOT reveal their public key — until they make their first outgoing transaction (which reveals the pubkey in the signature). This is why quantum computers threaten only addresses that have sent transactions.
- **`ecrecover` returns `address(0)` on failure** — ALWAYS check the return value is not `address(0)`, or use OpenZeppelin's `ECDSA.recover` which reverts on failure.
- **ECDSA malleability**: Every valid signature has a second valid form. Normalize `s` to the lower half (`s <= secp256k1n / 2`) and enforce it to prevent signature replay attacks.
- **Nonce reuse in signing = private key exposure**: If the same random nonce is used to sign two different messages, an attacker can solve two linear equations to extract the private key.
- **EIP-712 domain separators bind signatures** to a specific contract address and chain ID — critical for preventing cross-contract and cross-chain replay.

## 💻 Code Deep Dive / Mechanics

### 🔴 Vulnerable Pattern 1: Missing `address(0)` Check in `ecrecover`

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

// VULNERABLE: Missing address(0) check allows bypass when signature is invalid/malformed
contract VulnerableAuth {
    address public owner;
    mapping(bytes32 => bool) public usedHashes;

    constructor() {
        owner = msg.sender;
    }

    // This function should only allow the owner to withdraw
    // But a bug allows anyone to bypass it with a malformed signature
    function withdrawFunds(
        uint256 amount,
        bytes32 messageHash,
        uint8 v,
        bytes32 r,
        bytes32 s
    ) external {
        // BUG: ecrecover returns address(0) for invalid/malformed signatures
        // If owner == address(0) OR if the check below uses ==, this is bypassable
        address recovered = ecrecover(messageHash, v, r, s);

        // WRONG: No check for recovered == address(0)
        // An attacker submits a garbage signature → recovered = address(0)
        // If owner is somehow address(0), the check passes!
        require(recovered == owner, "Not authorized");

        // Also: no nonce/replay protection! Same signature works forever.
        (bool success,) = msg.sender.call{value: amount}("");
        require(success, "Transfer failed");
    }

    receive() external payable {}
}

// Attacker scenario:
// If the contract owner is initialized as address(0) (e.g., missing constructor args,
// or owner was set to address(0) via a bug), submitting any malformed (v,r,s)
// will have ecrecover return address(0), matching the "owner" — bypass!
```

**Attack Vector / Analysis**: The missing `address(0)` check is one of the most common `ecrecover` bugs. The EVM precompile at address `0x1` silently returns `address(0)` for any invalid signature — it does NOT revert. Any contract that compares the return value to an expected signer without first checking it's non-zero can be bypassed by submitting garbage bytes as the signature. Additionally, there's no nonce or hash uniqueness check, so a valid signature can be replayed indefinitely.

### 🔴 Vulnerable Pattern 2: Signature Replay Due to Missing Chain ID & Nonce

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

// VULNERABLE: Signature replay attack — no chainId, no nonce, no contract address binding
contract ReplayableVault {
    address public owner;

    constructor(address _owner) {
        owner = _owner;
    }

    // The message the owner signs is just: keccak256(abi.encodePacked(to, amount))
    // PROBLEM 1: No nonce → same signed message is valid forever
    // PROBLEM 2: No chainId → same signature valid on testnet AND mainnet
    // PROBLEM 3: No contract address → same signature valid on any identical deployed contract
    function withdraw(
        address to,
        uint256 amount,
        bytes memory signature
    ) external {
        // Reconstruct the message hash — but it's missing critical context!
        bytes32 messageHash = keccak256(abi.encodePacked(to, amount));

        // Also missing: EIP-191 prefix! ecrecover without prefix won't match
        // what MetaMask signs (which uses personal_sign with the EIP-191 prefix)
        (bytes32 r, bytes32 s, uint8 v) = splitSignature(signature);
        address signer = ecrecover(messageHash, v, r, s);
        require(signer == owner, "Invalid signature");
        require(signer != address(0), "Invalid sig"); // at least this check exists

        (bool success,) = to.call{value: amount}("");
        require(success);
    }

    function splitSignature(bytes memory sig) internal pure returns (bytes32 r, bytes32 s, uint8 v) {
        require(sig.length == 65, "Invalid length");
        assembly {
            r := mload(add(sig, 32))
            s := mload(add(sig, 64))
            v := byte(0, mload(add(sig, 96)))
        }
    }

    receive() external payable {}
}

// Attack scenario:
// 1. Owner signs: withdraw(attacker, 1 ether) on testnet to test the system
// 2. Attacker saves that signature
// 3. Attacker replays the EXACT same bytes on mainnet → drains 1 ETH
// 4. Attacker replays again → drains another 1 ETH (no nonce consumed)
// 5. If the same contract is deployed at a new address, signature is still valid there
```

**Attack Vector / Analysis**: Real-world replay attacks have drained millions. The Nomad bridge hack had a variant of this — a missing validation in message processing meant any message (including old ones) could be replayed. Here, the fix requires including `nonce`, `chainId`, `address(this)` in the signed data structure — exactly what EIP-712 mandates.

### 🟢 Secure Implementation: OpenZeppelin ECDSA + EIP-712

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/utils/cryptography/ECDSA.sol";
import "@openzeppelin/contracts/utils/cryptography/EIP712.sol";

// SECURE: Uses EIP-712 for structured, replay-protected signing
contract SecureVault is EIP712 {
    using ECDSA for bytes32;

    address public owner;
    mapping(uint256 => bool) public usedNonces;

    // EIP-712 TypeHash for the Withdraw operation
    // Must match exactly what the signer's wallet will hash
    bytes32 public constant WITHDRAW_TYPEHASH = keccak256(
        "Withdraw(address to,uint256 amount,uint256 nonce,uint256 deadline)"
    );

    event Withdrawn(address indexed to, uint256 amount, uint256 nonce);

    constructor(address _owner)
        EIP712("SecureVault", "1") // name + version → domain separator
    {
        owner = _owner;
    }

    function withdraw(
        address to,
        uint256 amount,
        uint256 nonce,
        uint256 deadline,
        bytes memory signature
    ) external {
        // 1. Check deadline hasn't passed (prevents stale signatures)
        require(block.timestamp <= deadline, "Signature expired");

        // 2. Check nonce hasn't been used (prevents replay)
        require(!usedNonces[nonce], "Nonce already used");
        usedNonces[nonce] = true;

        // 3. Build the EIP-712 struct hash
        bytes32 structHash = keccak256(abi.encode(
            WITHDRAW_TYPEHASH,
            to,
            amount,
            nonce,
            deadline
        ));

        // 4. Get the EIP-712 typed data hash (includes domain separator automatically)
        // Domain separator encodes: name, version, chainId, address(this)
        // This prevents cross-chain and cross-contract replay!
        bytes32 digest = _hashTypedDataV4(structHash);

        // 5. Recover signer — ECDSA.recover (from OZ) reverts on address(0)
        // It also enforces s ≤ secp256k1n/2 (prevents malleability)
        address signer = digest.recover(signature);

        // 6. Authorize
        require(signer == owner, "Invalid signature");

        // 7. Execute
        (bool success,) = to.call{value: amount}("");
        require(success, "Transfer failed");

        emit Withdrawn(to, amount, nonce);
    }

    receive() external payable {}
}

// Off-chain signing (TypeScript/ethers.js):
/*
const domain = {
    name: "SecureVault",
    version: "1",
    chainId: await provider.getNetwork().then(n => n.chainId),
    verifyingContract: vaultAddress,
};
const types = {
    Withdraw: [
        { name: "to", type: "address" },
        { name: "amount", type: "uint256" },
        { name: "nonce", type: "uint256" },
        { name: "deadline", type: "uint256" },
    ],
};
const value = { to: recipientAddress, amount: parseEther("1"), nonce: 0, deadline: futureTimestamp };
const signature = await signer._signTypedData(domain, types, value);
*/
```

**Why this is secure**: 
- `EIP712._hashTypedDataV4()` automatically includes the domain separator (which contains `chainId` and `address(this)`) — preventing cross-chain and cross-contract replay.
- Nonce tracking prevents replay of the same signature twice.
- Deadline prevents stale signatures from being valid forever.
- `ECDSA.recover()` (OZ library) reverts instead of returning `address(0)`, and enforces low-s normalization against malleability.

### Keccak256 in Practice — Storage Slot Arithmetic

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract StorageLayout {
    // slot 0: owner
    address public owner;
    // slot 1: balances mapping
    mapping(address => uint256) public balances;
    // slot 2: nested mapping
    mapping(address => mapping(address => uint256)) public allowances;

    // The storage slot for balances[alice] is:
    // keccak256(abi.encode(alice, 1))  ← 1 is the mapping's slot number
    //
    // The storage slot for allowances[alice][bob] is:
    // keccak256(abi.encode(bob, keccak256(abi.encode(alice, 2))))

    function getBalanceSlot(address user) public pure returns (bytes32) {
        return keccak256(abi.encode(user, uint256(1)));
    }

    function readStorageSlot(bytes32 slot) public view returns (bytes32 value) {
        assembly {
            value := sload(slot)
        }
    }
}
```

import "forge-std/Test.sol";
import "@openzeppelin/contracts/utils/cryptography/ECDSA.sol";
import "@openzeppelin/contracts/utils/cryptography/MessageHashUtils.sol";

contract ECDSATest is Test {
    using ECDSA for bytes32;

    // Foundry's test cheatcode: vm.addr(privateKey) gives the address,
    // vm.sign(privateKey, hash) signs the hash and returns (v, r, s)
    uint256 constant ALICE_PK = 0xA11CE; // never use predictable keys in prod!
    address alice;

    function setUp() public {
        alice = vm.addr(ALICE_PK);
    }

    function testEIP191PersonalSign() public view {
        // Simulate what MetaMask does with eth_sign / personal_sign
        bytes32 rawHash = keccak256(abi.encodePacked("Hello, Ethereum!"));

        // Apply EIP-191 prefix (what wallets do automatically)
        bytes32 ethSignedHash = MessageHashUtils.toEthSignedMessageHash(rawHash);

        // Sign with Foundry cheatcode
        (uint8 v, bytes32 r, bytes32 s) = vm.sign(ALICE_PK, ethSignedHash);

        // Recover and verify
        address recovered = ECDSA.recover(ethSignedHash, v, r, s);
        assertEq(recovered, alice, "Signer mismatch");
        console.log("EIP-191 personal sign verified. Signer:", recovered);
    }

    function testMissingAddress0Check() public view {
        // Demonstrate that ecrecover returns address(0) for garbage input
        bytes32 hash = keccak256("some message");

        // Submit garbage signature bytes
        address recovered = ecrecover(hash, 28, bytes32(0), bytes32(0));
        assertEq(recovered, address(0), "Should return address(0) for invalid sig");

        // This is what a VULNERABLE contract would compare against owner!
        // If owner == address(0), this bypass would work.
        console.log("ecrecover with garbage signature returned:", recovered);
    }

    function testMalleability() public view {
        // secp256k1 curve order n
        uint256 n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141;

        bytes32 hash = keccak256("sign me");
        (uint8 v, bytes32 r, bytes32 s) = vm.sign(ALICE_PK, hash);

        // Compute the malleable counterpart: s' = n - s
        bytes32 malleable_s = bytes32(n - uint256(s));
        uint8 malleable_v = v == 27 ? 28 : 27;

        // Both recover the same address!
        address original = ecrecover(hash, v, r, s);
        address malleable = ecrecover(hash, malleable_v, r, malleable_s);

        assertEq(original, alice);
        assertEq(malleable, alice); // same signer!
        console.log("Both s and n-s produce valid signatures for the same signer");

        // OpenZeppelin's ECDSA.recover() would REVERT on the malleable form
        // because it checks: require(uint256(s) <= 0x7FFFF...., "ECDSA: invalid signature 's' value")
    }
}
```

forge test --match-contract ECDSATest -vvvv
```

| Real-World Hack | Loss | Root Cause |
|---|---|---|
| **PlayStation 3 (not Ethereum, but ECC)** | Entire platform compromised | Sony reused the same ECDSA nonce `k` for every signature, allowing private key extraction |
| **OpenSea NFT Cancellations Bypass** | NFTs relisted after cancellation | ECDSA signature malleability — the second valid form of a cancelled signature was accepted |

| **Wintermute (Sep 2022)** | $160M | Hot wallet address generated with vulnerable Profanity tool — private key brute-forced |
